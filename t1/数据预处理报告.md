# 问题一：数据预处理报告

## 1. 预处理目标与原则

问题一的数据预处理服务于后续三项并列任务：工作负载统计分析、短期负荷预测和基础算力调度。处理遵循以下原则：

1. **保留原始任务粒度**：以每条 `TaskID` 记录为最小处理单元，不聚合、不抽样、不删除任务；
2. **统一资源量纲**：将任务需求统一换算为 GPU-hour，将任务 IT 能耗统一换算为 MWh；
3. **显式校验数据接口**：读取后先检查各文件的必需字段和任务类型映射，发现缺失即停止计算；
4. **时间序列补零而不插值**：对“该小时无该区域、该类型任务到达”的组合补零，零表示真实的无到达需求，而非缺失值；
5. **预测与调度数据解耦**：预处理生成的逐时序列供统计与预测使用；调度模块仍以原始任务表的实际到达记录为输入。

---

## 2. 原始数据与字段核验

预处理程序读取 5 份输入表，字段要求如下。任一必需字段缺失时，程序抛出错误并停止，避免字段错位导致后续模型失真。

| 数据文件 | 作用 | 核验字段 |
|---|---|---|
| `workload_trace.xlsx` | 任务轨迹与 SLA 参数 | `TaskID`、`TaskType`、`ArrivalHour`、`GPU_Demand`、`EstimatedDuration_min`、`SourceRegion`、`MaxLatency_ms`、`LatestFinishHour` |
| `GPU_information.xlsx` | 各区域 GPU、IT 功率和 PUE 容量 | `Region`、`Available_GPU`、`Max_IT_Power_MW`、`PUE`、`Max_Facility_Power_MW` |
| `network_latency.xlsx` | 区域间单向网络时延 | `FromRegion`、`ToRegion`、`NetworkLatency_ms` |
| `power_mapping.xlsx` | 不同任务类型的单位等效 GPU 功率 | `TaskType`、`GPU_Power_MW_per_EquivalentGPU` |
| `region_time_data.xlsx` | 区域逐时非 AI IT 负荷 | `Hour`、`Region`、`NonAI_IT_Load_MW` |

本题任务轨迹共保留 **50000 条**记录；未进行行删除、离群值截断、均值填补或随机重采样。这样可确保调度模型面对的是题目给定的完整实际任务集合。

---

## 3. 任务表标准化与派生变量构造

### 3.1 数据类型与原始粒度

任务表中的任务到达时间保留为小时索引 `ArrivalHour`；任务运行时长的原始单位为分钟；区域和任务类型保留为分类字段。每项任务在后续处理过程中始终使用其原始 `TaskID` 追踪。

### 3.2 时长换算

将原始任务时长由分钟换算为小时：

```
Duration_h(i) = EstimatedDuration_min(i) / 60
```

该变量保留小数精度，避免将分钟级时长直接向上或向下取整而造成资源需求失真。调度阶段据此计算任务与每个小时的精确重叠时长。

### 3.3 GPU-hour 需求量纲

不同任务的 GPU 数量和持续时间同时影响其资源占用，因此统一构造 GPU-hour：

```
GPU_h(i) = GPU_Demand(i) × Duration_h(i)
```

该指标是统计分析和短期预测的标准需求量纲。由 50000 条任务汇总得到总需求 **5,020,786.65 GPU-hour**。

### 3.4 IT 能耗量纲

将 `power_mapping.xlsx` 转换为任务类型到单位等效 GPU 功率的映射：

| 任务类型 | 单位等效 GPU 功率（MW/GPU） |
|---|---:|
| RealTimeInference | 0.08 |
| BatchInference | 0.10 |
| AITraining | 0.16 |

程序检查任务表中全部 `TaskType` 是否均可在该映射中找到；若存在未映射类型则停止计算。任务 IT 能耗按下式构造：

```
IT_MWh(i) = GPU_h(i) × GPU_Power_MW_per_EquivalentGPU(TaskType_i)
```

全体任务汇总 IT 能耗为 **738,927.99 MWh**。该指标用于识别不同类型任务的能源侧贡献，同时为调度模型的 IT 功率约束提供类型功率参数。

## 4. 区域参数与约束数据整理

### 4.1 区域集合与容量索引

以 `GPU_information.xlsx` 中的 `Region` 字段建立区域集合：RegionA–RegionF。随后按区域建立以下可查询参数：

- `Available_GPU`：区域可用等效 GPU 数量；
- `Max_IT_Power_MW`：区域最大 IT 功率；
- `PUE`：电能使用效率；
- `Max_Facility_Power_MW`：最大设施侧功率。

### 4.2 设施功率一致性校验

对每个区域执行如下核验：

```
Max_Facility_Power_MW = Max_IT_Power_MW × PUE
```

程序采用绝对误差不超过 `1e-6` 的数值容差进行比较。全部区域通过该关系核验，因此设施侧功率约束由 IT 功率约束数学蕴含，后续基础调度模型仅保留 IT 功率约束，避免重复计约束。

### 4.3 时延映射表

将网络时延表整理为键值映射：

```
(SourceRegion, ExecRegion) → NetworkLatency_ms
```

调度阶段直接依据该映射筛选满足任务 `MaxLatency_ms` 的候选执行区域；预处理不对时延数据进行插补或对称化，保留原表给出的单向时延口径。

### 4.4 非 AI 负荷与可用 IT 功率余量

从逐时区域负荷表提取：

```
Hour, Region, NonAI_IT_Load_MW
```

并按区域连接最大 IT 功率，构造每小时可供 AI 任务使用的 IT 功率余量：

```
IT_Power_Margin_MW(r,t) = Max_IT_Power_MW(r) − NonAI_IT_Load_MW(r,t)
```

该时序表既用于统计功率紧约束，也直接进入调度模型的容量检查。处理结果表明，RegionA、RegionB、RegionC 的最小余量分别为 18.98 MW、18.21 MW、17.37 MW，说明东部区域的 IT 功率约束较紧。

## 5. 面向统计与预测的时间序列构造

### 5.1 区域—类型—小时聚合

基于已构造的 `GPU_h`，按到达小时、来源区域和任务类型聚合：

```
y_(r,τ)(t) = Σ[g_i × Duration_h(i)]
            i: ArrivalHour_i=t, SourceRegion_i=r, TaskType_i=τ
```

其中 r 为 6 个区域，τ 为 3 类任务，共形成 18 条小时级 GPU-hour 需求序列。

### 5.2 完整时间索引与零值补齐

将时间索引统一重建为 0–2399 小时，并构造全部 6×3 个“区域—类型”列组合。对原始聚合结果中不存在的小时—区域—类型组合填充为 `0.0`。

此处的补零含义明确：该组合在该时段没有任务到达，不是缺失观测。因此，补零既保持了 18 条序列的时间对齐，也保留了稀疏到达过程的真实特征；未使用均值、前向填充或插值来人为平滑需求波动。

### 5.3 日内剖面构造

对完整逐时序列按 `ArrivalHour mod 24` 分组并求均值，得到 24 个小时位置的典型日内 GPU-hour 需求剖面。该结果用于统计性展示和周期性特征验证，不会替代原始逐时序列参与调度。

## 6. 输出数据集及其用途

| 输出文件 | 内容 | 下游用途 |
|---|---|---|
| `region_type_task_count.csv` | 区域×类型任务数透视表 | 任务结构统计与图表 |
| `region_type_gpuh.csv` | 区域×类型 GPU-hour 透视表 | 资源需求统计与图表 |
| `region_type_it_energy.csv` | 区域×类型 IT 能耗透视表 | 能耗结构统计 |
| `task_type_summary.csv` | 任务类型的数量、GPU-hour、IT 能耗及占比 | 总体工作负载画像 |
| `hourly_region_type_gpuh.csv` | 18 条完整小时级 GPU-hour 序列 | 短期预测的输入与评价基准 |
| `daily_profile_gpuh.csv` | 24 小时日内平均剖面 | 周期性统计分析 |
| `it_power_margin_timeseries.csv` | 区域逐时 IT 功率余量 | 调度容量约束与功率统计 |
| `it_power_margin_summary.csv` | 各区域 IT 余量最小、平均、最大值 | 功率紧约束判定 |

需要强调的是，`hourly_region_type_gpuh.csv` 只供统计分析和短期预测模块使用。基础调度模块不读取预测输出，而是直接读取保留完整任务粒度的 `workload_trace.xlsx` 任务记录，以及上述区域容量、时延和逐时非 AI 负荷数据。

## 7. 预处理结果核查

预处理完成后，采用以下一致性检查保证数据可用性：

1. **字段完整性**：5 份输入表均通过必需字段核验；
2. **类型映射完整性**：任务表中的全部任务类型均有功率映射；
3. **设施功率一致性**：所有区域均满足 `Max_Facility_Power_MW = Max_IT_Power_MW × PUE`；
4. **时间轴完整性**：逐时需求序列覆盖 0–2399 的全部 2400 个小时，且包含完整的 18 个区域—类型组合；
5. **统计量纲一致性**：任务数、GPU-hour 与 IT 能耗均由同一份任务级数据汇总得到；
6. **任务保真性**：50000 条原始任务不经删除或合成地进入基础调度模块。

通过以上处理，原始异构表被整理为任务级、区域级与逐时序列级三类一致的数据接口，为问题一的统计、预测和调度提供可追溯的数据基础。
